# Phase 02.1: Walking Skeleton on GNOME 50 - Research

**Researched:** 2026-10-17
**Confidence:**
- HIGH for the host capability facts (probed)
- MEDIUM for the portal Clipboard+EIS behaviour on GNOME 50 (spec-backed, not yet exercised on this host)
- LOW for model latency (not yet benchmarked)

## 1. Why the original insertion plan fails here

| Mechanism | Needs | GNOME 50 status | Verdict |
|---|---|---|---|
| `wl-copy` / arboard data-control | `ext-data-control-v1` or `wlr-data-control` | Not implemented by Mutter | Background write fails or grabs focus (Handy #1742, #1549) |
| `wtype` | `zwp_virtual_keyboard_v1` | Not implemented by Mutter | Fails (Handy #2006) |
| `ydotool` / `dotool` | rw `/dev/uinput` | root-only on this host | Needs a udev rule or group change. Privileged, layout-unaware |
| X11 XTest (`xdotool`, enigo) | XWayland focus | Only XWayland apps | Not a Wayland solution (Handy #429) |
| **RemoteDesktop + Clipboard portal + EIS** | Portal v2 + libei | `RemoteDesktop` v2, `Clipboard`, `libei1` 1.5.0 present | **Use this.** One consent dialog, persisted via restore token |
| GNOME Shell extension (St.Clipboard + Clutter virtual device) | User installs an extension | Works, but version-coupled | Fallback / Phase 4 overlay |

## 2. Portal sequence (proposed)

```text
Registry.Register("dev.voxflow.VoxFlow")
RemoteDesktop.CreateSession(session_handle_token)
RemoteDesktop.SelectDevices(session, {types: 1 /*KEYBOARD*/, persist_mode: 2, restore_token?})
Clipboard.RequestClipboard(session, {})          # must precede Start
RemoteDesktop.Start(session, parent_window="", {})  -> {devices, clipboard_enabled, restore_token}
RemoteDesktop.ConnectToEIS(session, {})          -> fd  (libei receiver context)

per dictation:
  wait trigger Deactivated (+ ~30 ms for modifier release)
  Clipboard.SetSelection(session, {mime_types: ["text/plain;charset=utf-8","text/plain"]})
  on SelectionTransfer(session, mime, serial):
      fd = SelectionWrite(session, serial); write(utf8); close; SelectionWriteDone(session, serial, true)
  EIS: keyboard key(KEY_LEFTCTRL down) key(KEY_V down) frame; key(V up) key(CTRL up) frame
```

Open questions for the spike (record the answers in HOST-ACCEPTANCE):
- Does GNOME 50 show a persistent "remote control" indicator in the top bar while the session is open? If so, is that acceptable UX, or should the session open per dictation (adds about 50–150 ms)?
- Is the restore token honoured across logout for unsandboxed apps once registered?
- Does `Clipboard.SetSelection` work with a keyboard-only session (no ScreenCast)?
- Keycodes: the EIS device keymap is XKB. Resolve `Control_L` and `v` through xkbcommon so non-QWERTY layouts work (Handy #439, #2004).

## 3. GlobalShortcuts v1 hold/release

v1 defines both `Activated` and `Deactivated` with timestamps. The existing `platform/shortcuts.py` only claims hold support after observing both signals. The spike must record whether GNOME 50 emits `Deactivated` on physical key release, or immediately after `Activated`. Toggle mode is the documented fallback.

## 5. Handy lessons applied to this phase

- Inject only after trigger release (#429)
- One chord paste, not per-character typing (#429, #439, #2184)
- Keymap-derived keycodes (#2004)
- No clipboard restore yet (#502)
- Report `sent`, never "delivered" (#2275)
- Stall watchdog on capture (#2113)
- No playback chimes in this phase (#1973)
