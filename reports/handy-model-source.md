# Handy Models Can Guide VoxFlow Safely

**Bottom line:** VoxFlow can use some of the same underlying model families as Handy, but it cannot load Handy’s `.gguf` or legacy `.bin` files through the current `faster-whisper` provider. Handy is a Tauri/Rust desktop application built around the native `transcribe-cpp` runtime, while VoxFlow currently expects a CTranslate2 model directory containing `config.json` and `model.bin`. Handy’s strongest reusable ideas are its immutable model identity, SHA-256 verification, explicit local model management, and native-worker isolation. **Recommendation:** keep VoxFlow’s existing `faster-whisper` path as the default and add a separate, opt-in native provider for one pinned Whisper GGUF artifact, with model bytes remaining user-managed. The Whisper GGUF repositories are the safest first candidates because the catalog identifies them as Apache-2.0 and their architecture is closest to VoxFlow’s existing provider. **Unresolved host validation:** no Handy-format model has yet been loaded through a VoxFlow-compatible helper on the target Ubuntu GNOME/Wayland host, so native loading, latency, cancellation, and backend behavior still require a host spike.

## Handy couples a native ASR engine to a recoverable desktop pipeline

**Fact.** At commit [`9e57a0d7929fcc6417ea0d6e54c1b57f62635edd`](https://github.com/cjpais/Handy/tree/9e57a0d7929fcc6417ea0d6e54c1b57f62635edd), Handy 0.9.8 is a Tauri 2 application with a React/TypeScript frontend and Rust backend. Its product loop is shortcut activation, audio capture, local VAD and transcription, then paste-back into the focused application. Native inference runs in a separate worker process: the supervisor sends framed JSON and PCM data, while the worker loads the model with `transcribe_cpp::Model::load_with` and runs batch or streaming sessions. This process boundary is designed to contain native or GPU crashes and permit recovery, rather than being required for the model format itself ([`src-tauri/Cargo.toml`](https://github.com/cjpais/Handy/blob/9e57a0d7929fcc6417ea0d6e54c1b57f62635edd/src-tauri/Cargo.toml#L68-L86), [`engine_supervisor/worker.rs`](https://github.com/cjpais/Handy/blob/9e57a0d7929fcc6417ea0d6e54c1b57f62635edd/src-tauri/src/engine_supervisor/worker.rs#L255-L320)).

**Fact.** Handy separates ASR from speech detection. Its default VAD is a GGUF-converted Silero VAD model, with Earshot as an alternative; its capture path uses 16 kHz mono audio and smoothing around onset and hangover. For long recordings, VAD also scores pauses for chunking. This is useful architecture evidence, but it does not imply that VoxFlow should move model-specific resampling into its capture callback: VoxFlow already records a negotiated source-format WAV and should normalize at a provider boundary ([`audio/sink.rs`](https://github.com/cjpais/Handy/blob/9e57a0d7929fcc6417ea0d6e54c1b57f62635edd/src-tauri/src/audio_toolkit/audio/sink.rs#L165-L193), [`vad/smoothed.rs`](https://github.com/cjpais/Handy/blob/9e57a0d7929fcc6417ea0d6e54c1b57f62635edd/src-tauri/src/audio_toolkit/vad/smoothed.rs#L54-L119)).

## Explicit downloads become offline local inference

**Fact.** Handy uses two local storage layers. Catalog downloads use `hf-hub` and normally reuse the Hugging Face cache, while `get_model_path` also checks the application’s `models` directory; on Linux the documented normal location is typically `~/.config/com.pais.handy/models/`. Portable mode redirects both locations under the executable’s `Data/` directory. If Hugging Face acquisition fails, Handy downloads the pinned artifact from its mirror into the app model directory, resumes `.partial` files, checks size and SHA-256, and atomically renames the completed file ([`model.rs`](https://github.com/cjpais/Handy/blob/9e57a0d7929fcc6417ea0d6e54c1b57f62635edd/src-tauri/src/managers/model.rs#L2120-L2177), [`portable.rs`](https://github.com/cjpais/Handy/blob/9e57a0d7929fcc6417ea0d6e54c1b57f62635edd/src-tauri/src/portable.rs#L14-L69), [`download.rs`](https://github.com/cjpais/Handy/blob/9e57a0d7929fcc6417ea0d6e54c1b57f62635edd/src-tauri/src/managers/model/download.rs#L51-L119)).

**Fact.** Handy’s offline claim applies after acquisition: the catalog is compiled into the binary, and transcription requires no network or cloud account once the selected ASR weight and VAD resource are present. First-time downloads, missing models, and optional updates still require network access; restricted-network users can manually install weights according to the README ([offline behavior](https://github.com/cjpais/Handy/blob/9e57a0d7929fcc6417ea0d6e54c1b57f62635edd/README.md#L5-L16), [manual installation](https://github.com/cjpais/Handy/blob/9e57a0d7929fcc6417ea0d6e54c1b57f62635edd/README.md#L285-L357)). **Recommendation:** VoxFlow should borrow the verification properties later, but keep model bytes user-managed now and avoid silently reusing Handy’s app-data directory or shared Hugging Face cache. That preserves the existing local-only and reproducible acceptance boundary.

**Fact.** The code and the weights have separate legal identities. Handy source is MIT-licensed, but Handy’s name, logo, icon, and brand assets are explicitly excluded from open-source reuse ([`LICENSE`](https://github.com/cjpais/Handy/blob/9e57a0d7929fcc6417ea0d6e54c1b57f62635edd/LICENSE#L1-L21), [branding terms](https://github.com/cjpais/Handy/blob/9e57a0d7929fcc6417ea0d6e54c1b57f62635edd/README.md#L471-L483)). The catalog records model-card licenses independently: 25 entries are Apache-2.0, 21 MIT, 15 CC-BY-4.0, 7 are `other`, and 1 is CC-BY-NC-4.0 ([`gen_catalog.py`](https://github.com/cjpais/Handy/blob/9e57a0d7929fcc6417ea0d6e54c1b57f62635edd/scripts/gen_catalog.py#L203-L259)). **Recommendation:** do not treat Handy’s MIT license as permission to redistribute any model. Preserve the applicable model license and `NOTICE` at the exact pinned revision; exclude CC-BY-NC by default and human-review NVIDIA Open Model License, FunASR, HAI-DEF/MedASR, and other nonstandard terms. This is an engineering compliance assessment, not legal advice.

## VoxFlow can reuse Whisper weights only through a new backend

**Fact.** The current VoxFlow adapter at [`src/voxflow/providers/local_whisper.py`](../src/voxflow/providers/local_whisper.py) is intentionally a lazy `faster-whisper`/CTranslate2 provider. It requires a directory containing `config.json` and `model.bin`, computes a directory checksum, passes that directory to `faster_whisper.WhisperModel` with `local_files_only=True`, and maps library segments into VoxFlow timestamps. A Handy `*.gguf` or legacy `ggml-small.bin` is a single native-runtime artifact, not a CTranslate2 directory, so changing only `model_id` cannot make it load. **Answer to the compatibility question:** VoxFlow can use the same upstream Whisper family, but not the same Handy artifact through the current provider; it needs a GGUF/GGML-capable backend.

**Fact.** VoxFlow already has the correct provider-independent seam. [`src/voxflow/providers/asr.py`](../src/voxflow/providers/asr.py) defines immutable `AudioInput`, cancellation, `TranscriptResult`, timestamped segments, and checksum binding, while [`src/voxflow/core/jobs.py`](../src/voxflow/core/jobs.py) owns validation, retry, and job state. **Recommendation:** add a sibling `local-whisper-cpp` provider rather than modifying `LocalWhisperProvider`. The provider should accept one explicit `.gguf` file, normalize source-format audio to the native engine’s required mono/16 kHz boundary, invoke a short-lived project-local helper without shell or network access, parse bounded JSON segments and language, and return the existing `TranscriptResult` with the original audio checksum.

**Recommendation.** Start with `handy-computer/whisper-small-gguf` for a lower CPU and memory baseline, or `handy-computer/whisper-medium-gguf` when multilingual coverage matters more. The notes identify all Whisper catalog repositories as Apache-2.0, and Whisper is the smallest architecture risk because VoxFlow already models Whisper transcription semantics. The Silero VAD conversion is a reasonable later candidate because its card identifies MIT licensing and includes a derived-file notice, but it should not be a prerequisite for the first provider spike; explicit push-to-talk boundaries and the existing capture/session behavior can be validated first.

**Unresolved host validation.** The target Ubuntu GNOME/Wayland environment still needs a real spike proving that the chosen native helper can load the pinned GGUF, consume VoxFlow’s negotiated WAV, emit stable timestamps and language metadata, terminate promptly on cancellation, recover from process failure, and meet cold-start and inference-latency targets on CPU and any available Vulkan path. The notes also leave the native-library-versus-subprocess choice open; a subprocess is the safer first experiment because it isolates native crashes and makes Python behavior deterministic. Parakeet, Canary, Cohere, Voxtral, Qwen, FunASR, Granite, Moonshine, GigaAM, and medical/special-license models should remain out of this first slice even though Handy can represent them as GGUF, because format compatibility does not remove architecture, capability, or licensing differences.

## A bounded spike preserves VoxFlow’s clean-room boundary

**Recommendation.** The smallest implementation path is a four-step vertical slice. First, pin one exact catalog tuple—repository ID, revision, filename, expected size, SHA-256, and license metadata—and place the model outside the application package under the existing explicit `--model-root` style of host-managed input. Second, add read-only discovery for a top-level `.gguf` file that reports backend, format, portable model ID, size, checksum, and availability without downloading or mutating files. Third, build the short-lived native helper and `local-whisper-cpp` adapter behind the existing `ASRProvider` contract. Fourth, add fake-helper tests for invocation arguments, malformed JSON, process failure, cancellation, checksum binding, and network absence, followed by one host-only acceptance row for real loading and timing.

| Preserve as VoxFlow-owned | Borrow as a design pattern | Do not copy from Handy |
|---|---|---|
| `ASRProvider`, `TranscriptResult`, `DictationJobRunner`, negotiated audio artifacts, local-only policy, and original audio checksum | Pinned revisions, expected size/hash, resumable partial files, atomic rename, explicit model scanning, capability probing, and native-worker failure isolation | Handy source or branding, its catalog text and score claims, direct desktop shortcut/signal strategy, `wtype`/`dotool`/`ydotool` defaults, automatic download-first onboarding, shared-cache assumptions, always-on capture, or focus-stealing overlays |

**Fact.** Handy’s own Linux notes document limitations around GNOME/Mutter and `wtype`, plus machine-specific `ydotool` setup and a clipboard/input fallback chain ([Linux notes](https://github.com/cjpais/Handy/blob/9e57a0d7929fcc6417ea0d6e54c1b57f62635edd/README.md#linux-notes), [`input.rs`](https://github.com/cjpais/Handy/blob/9e57a0d7929fcc6417ea0d6e54c1b57f62635edd/src-tauri/src/input.rs#L169-L178)). **Recommendation:** use Handy as evidence for model management and native isolation, not as a template for VoxFlow’s Wayland shortcut or paste path. VoxFlow’s compositor-mediated Global Shortcuts and clipboard-first insertion should remain the platform boundary.

## Conclusion

Handy demonstrates that one desktop product can offer a broad offline ASR catalog, but its model portability comes from the native `transcribe-cpp` backend, not from the model filenames alone. VoxFlow should therefore adopt the artifact discipline and failure isolation while retaining its own contracts, storage policy, branding, and Wayland integration. The practical decision is to validate one pinned Apache-2.0 Whisper GGUF through an isolated helper before considering any catalog, downloader, VAD replacement, or non-Whisper architecture; if that host spike fails its loading or cancellation criteria, the current `faster-whisper` baseline remains the safe default.
